# 原子收敛检查点（review-convergence checkpoint）

> 来源：`xindong/dash` `Skills/git/references/review-convergence.md` §1〜§3。案例背景：
> `makecindy/cindy#844`（2026-07，异步重试/退避改动）37 轮 review、41 个 commit、74 条 P1，
> 事后复盘约一半轮次来自补丁只修对称路径的一半；`#1211` 一个 UI 兜底问题的修复过程中长出
> 一整套锁子系统，25 轮后被整体扔掉才合并。本文档是该方法论在 pr-autopilot `submit-pr` 收口
> 链路里的落地契约，owner 与 lead 已就 D1〜D5 达成共识（各条见下方对应小节）。

## 触发条件（命中即停手，下一个修复 commit 前必须先产出六件套）

四条命中任一即触发（并列关系，不是替代；任一条命中即停手）：

1. 上一轮修复被指出（或自查发现）漏了对称的另一半——例如 resolve 分支修了、reject 分支
   没修；同步路径修了、迟到/乱序路径没修。
2. 同一语义的判据/guard 在代码里出现第 3 处——连续两次独立加了同一含义的检查，说明判据
   没有归一，继续加第 3 处只是把同一个洞打三个补丁。
3. repair-mode watermark（`SKILL.md`「收敛判据与收口」）计数到第 5 个 candidate 仍出现
   新 family。
4. **某个 `family_key` 在一个批次的 `frozen_families` 中被处置后，又出现在后续批次的
   `frozen_families` 里**（批次事务协议，issue #9 SC 延伸；i9-batch）。这条是批次协议对
   既有机制的**真实增量**：既有 1〜3 全是人判形状（"漏了对称一半"/"第 3 处判据"/"水位线到
   第 5 个"），本条**机器可判且更早**——`family_key` 逐字内容派生（`consensus-gate.mjs` 的
   `familyKeyOf`），跨批次出现即可比对；比等 5 个 candidate 或 2 轮窄面更早暴露「SC 一路绿、
   bug 一路复发」的捉老鼠成因。命中本条时，下一个修复 commit 前必须产出下方「复发归因段
   （recurrence）」——它是既有六件套的**补充载体**（回看上一次 SC 为什么失效，既有六件套
   从头到尾没有这一问），不是替代六件套；命名纪律：**「六件套」保持既有那套的唯一称谓**，
   本段不叫六件套。
   > **T1 边界（如实声明，lead 2026-08-07 措辞）**：批次协议拦的是**逐字复发**，拦不住
   > **语义复发**——`family_key` 由 `invariant` 的字面文本派生（仅 trim/小写/去空白），
   > 同一根因换个说法会算出不同 key、机器视为新族。语义级同族复发的判断权在 lead，机器
   > 无能力。上面「机器可判且更早」说的是优点；本条边界说的是它**治不了什么**——反捉老鼠
   > 的痛点本体就是语义复发，本机制只拦逐字复发，不冒充已解决语义复发。

## 原子性（D1，硬约束）

六件产出必须**一次性全部完成**才允许提交下一个修复 commit。拆开做——比如这次 commit 只写
不变量、下一次才补测试——**等于没做**：检查点的价值在于修复前先看清全貌，分两次做就退化回
「打一个补丁再看下一条」的老路，触发条件不会因为你做了一半就停止计数。lead 派工时必须把
六件套当成**一个不可拆的整体**（同一 SC 或同一 fix-plan 分组内的强制串行子任务），不得让
worker 先 commit 部分产出。

## 六件套

1. **每个失败族一句话可判定不变量**：把本轮涉及的每个失败族（用下方词典或临场归纳）写成
   一条可判定的不变量。例：「取消后任何迟到的 start 都不得重新激活」。写不出可判定的不变量
   （无法一眼看出某段代码是否满足它）不算完成这一步。
2. **每个状态字段的唯一写入 owner**：为每个状态字段指定唯一写入者与生命周期；发现同一字段
   有多个写入者，先把它们收拢成一个，再继续下一步——多写入者本身就是下一次「漏了对称一半」
   的根因。
3. **D4：事件 × 状态矩阵**——枚举全部事件 × 全部状态，**每格必须写「动作/忽略/拒绝/
   不可能」之一并附一句理由**——空格 = 没想过的路径，禁止留白；判为「不可能」也要写为什么
   不可能，不能用留空表示「这个我已经判断过是 N/A」（留白与「判过是 N/A」在检查点里必须
   看得出区别，否则复核者无法分辨是漏项还是已排除）。
4. **对称路径审计**：resolve / reject / timeout / cancel / close / 乱序 / 重复 / 迟到，
   逐条对照第 3 步的矩阵检查现有代码——这是本检查点的核心，触发条件①「漏了对称的另一半」
   直接对应这一步，也是本检查点存在的主要理由。
5. **判据归一**：同一语义只留一个判据、一条清理路径，所有入口复用；触发条件②里出现的第 3
   处判据在这一步应当被合并掉，而不是任由它继续存在、之后再长出第 4 处。
6. **可鉴别交错测试**：新测试必须能区分「正确修法」与「上一轮那种只修一半的修法」——对旧
   补丁应当红。这不是独立于 `hardening-checklist.md` 第 8 类之外的新判据，是第 8 类反向
   变异判据针对检查点场景的专项应用（见该文件「检查点专项：可鉴别的半修法回归」小节，
   SC-B5）。优先写事件交错序列测试与性质测试，不要逐条 review 评论各配一个孤立回归用例——
   `#844` 累计 +3732 行测试仍压不住组合爆炸，就是后一种写法的下场。

## D2：数字线与六件套的权限边界（与「拒绝数字轮次闸」立场的调和）

`SKILL.md`「收敛判据与收口」一直明确拒绝「跑够 N 轮就停」的数字闸——理由是数字闸切早漏真
问题、切晚继续螺旋。repair-mode watermark（见 `SKILL.md`，第 5 / 第 10 个 candidate）不是
对这个立场的推翻，是**范围收窄后的正交机制**：它**只**切换「这一次修复要不要先做六件套 /
要不要禁止继续同形状打补丁」这一个开关，**绝不**触碰：

- consensus-gate 是否 PASS；
- finding 的 severity 判定；
- 某条 finding 能否走 `[ARCHIVE]`；
- push-guard 是否放行。

这四件事仍然分别由各自的脚本/审查席独立裁决，水位线到第几个 candidate 不改变它们的判据。
即使水位线已经强制了六件套或升级路径，PR 依然可能因为其他原因迟迟不能收口——这正是设计
目的：数字只管「怎么修」，不管「能不能收口」，后者永远是形状判据（连续同族复发/blocker
不减）说话。

## D3：owner 决策范围（升级阶梯「哪些选项需要 owner」的判据来源）

拆 PR、净新增基础设施、用户可见行为/功能范围/发布策略变更——这三类需要 owner 决策；纯
技术升级路径（状态机化、职责上移、缩减实现机制但保留产品语义的降级设计）lead 自主选，
不需要上抛。`SKILL.md`「收敛判据与收口」第 5 条（升级阶梯）与 `hardening-checklist.md`
「新增机制确认门」都以此为界。

**判据不是自称**：技术路径怎么选是 lead 的判断，但要不要缩小用户能看到的范围/能力（划定
范围本身就是功能范围变更）、要不要拆成多个 PR、要不要新增一整类机制——这些属于产品/发布
决策，不能因为「这轮是我在改代码」就默认自己能决定；同样，「我选的是降级设计、声称保留了
产品语义」也不能自动免检——保留没保留看的是改动后用户可见行为是否真的没变，不是选择的
名字叫不叫「降级」。

## D5：五族失败词典（条件型——命中异步生命周期/重试/取消/并发形状才逐条对照，不对纯同步代码强制）

来源：`review-convergence.md` §1。按不变量归类反馈：同一条被破坏的不变量下的所有表现算
一族，reviewer 换文件、换入口、换措辞不改变族别。只有一条反馈时同样适用——先归因到不变量，
修复覆盖该不变量的全部路径（包括没被点名的位置），不是只修被点名的那一处。

| 失败族 | 典型表现 |
|---|---|
| 结算路径不对称 | resolve 修了 reject 没修；同步路径修了、迟到/乱序路径没修；cancel 前修了、cancel 后没修 |
| 迟到事件重新激活 | 取消/结算之后，迟到的 start / callback / RPC 响应把已终结的生命周期重新拉活 |
| 终态重复 | 终态事件（完成/失败/取消）被发出两次，或被两条独立路径分别发出 |
| 控制信号当数据 | 控制事件（心跳、进度、重试提示）被当成模型输出/业务数据处理 |
| 约束因重试放宽 | 重试、恢复路径绕过了首次路径本该有的权限或前置检查 |

判断「同族复发」的标准：新反馈指向的不变量与已修过的一条相同——这时它不是又一个独立 bug，
是上一轮的修法没有覆盖该不变量的全部路径，继续逐条打补丁只会制造下一轮。

> 本词典**不是**穷尽列表，是异步生命周期类改动里已被真实咬过的五族；命中不属于任一族的新
> 形状仍按第 3 步（事件×状态矩阵）临场归纳，不因词典没列到就跳过对称路径审计（第 4 步）。

## 六件套产出去向

产出贴进 PR body 的**独立** checkpoint marker 段（`<!-- pr-autopilot:checkpoint:start/end -->`，
D4，与 MUST-FIX/ARCHIVE 的不变量锚点段用**不同**的 marker，互相独立 upsert、互不覆盖——
两者共用同一对 marker 曾是本文档与 `SKILL.md` 之间的一处矛盾：任何一方重新生成都会把另一方
整段吃掉，2026-08-02 gpt 终审阻断项）。写法：
```
node scripts/pr-body.mjs --artifact consensus.json --sc-manifest sc-manifest.json \
  --checkpoint-json checkpoint.json [--existing-body <当前 PR body 文件>]
```
`checkpoint.json` 结构对应六件套：`{ trigger, invariants:[{family,statement}],
state_owners:[{field,owner,lifecycle}], event_state_matrix:[{event,state,action,reason}],
symmetry_audit:[{path,status,note}], normalization:[{semantic,consolidated_to}],
tests:[{name,distinguishes}] }`——`scripts/pr-body.mjs` 的 `buildCheckpointSection` 只负责
渲染，不判断六件套是否齐全（那仍是 lead 派工/收口时的过程纪律，见上方 D1 原子性）。

**复发归因段（recurrence，可选字段，仅触发条件④命中时必填）**：`checkpoint.json` 的
顶层可选字段，不占六件套名额、不叫六件套。结构：

```json
{
  "recurrence": {
    "family_key": "fk1-…",                  // 复发的族（必须 ∈ 本批 frozen_families）
    "prior_batch_id": "…",                  // 上次在哪个批次被处置
    "prior_candidate_sha": "…",             // 上次的修复 commit
    "prior_sc_id": "SC-…",                  // 上次声称拦住它的 SC（必须 ∈ sc manifest）
    "prior_sc_missed_because": "…",         // 自由文本：那条 SC 为什么没拦住（T1 只验非空）
    "verdict": "fix_was_wrong" | "family_was_misgrouped" | "fix_was_symptom",
    "root_cause_locator": "路径:行号"        // 仅当 verdict="fix_was_symptom" 时必填
  }
}
```

对照 lead 原六问的压缩：①②③ 收成 `prior_sc_id` + `prior_sc_missed_because`；④「修错还是
族归错」是 `verdict` 二选一；⑤⑥「根因还是症状」是 `verdict` 第三值 + 症状时强制
`root_cause_locator`。结构化枚举比六段自由文本更可判。

**齐全性检查在批次闭合门（`scripts/batch-closure-gate.mjs`），不在 `pr-body.mjs`**——
`buildCheckpointSection` 只渲染、不判断齐全的职责边界不扩。闭合门验：recurrence 字段齐全 +
`verdict` enum 合法 + symptom 时 `root_cause_locator` 非空（形如 `路径:行号`）+ `family_key`
∈ 本批 `frozen_families` + `prior_sc_id` ∈ sc manifest。保证等级 **T1（防疏忽不防伪造，
如实声明）**：`prior_sc_missed_because` 填一句废话也能过，机器只锁形状与自洽；「这次是不是
真的同族复发」的判断权在 lead（机器无跨批次账本，无法独立判定），申报后由机器验形状。
半残/重复 marker（只有 start、只有 end、重复 start）→ 脚本 fail loud 拒绝写入，不会静默
在文档里堆出第二段。
产出同时服务三个读者：自己下一步修复时的模型、lead 判断是否收敛的依据、审查席复核 delta
时的判据来源——`review-convergence.md` §2 原文称之为「reviewer 有了明确不变量后反馈会明显
更聚焦，不再每轮换个入口挑一条」。

## 批次严格后代不变量（lead 2026-08-07 定案，防后人误加回重复检查）

批次的 successor 必是 `source_candidate` 的**严格后代**（任意距离，不得等于起点）——批次是
「一批 finding → 一个已解决状态」的事务，多 commit 分步修复合法，不要求直接子 commit。

该不变量由 push-guard 的 `expected_sha` 绑定 + SC-3（终版 artifact 的 parent 祖先绑定）
**by construction 共同保证**；实测确认「非后代/零推进」在完整链上**无法独立构造触发**
（会被前置检查先拦）。

**因此批次门不再重复校验 —— 这不是疏漏，是刻意不加**：一道不可达的检查会让人误以为是它
在拦，而真正的强制点在别处（比没有这道门更危险——它正是「声明看着在验、实际没验」这个
本项目反复咬人的缺陷形状）。后人若要在此处加「严格后代」守卫，须先证明 `expected_sha` +
SC-3 存在可独立构造的失效路径（带实证，不是「未来可能变松」的推测），否则按「新增机制确认
门」不建。
