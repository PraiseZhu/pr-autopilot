# 加固清单（九类）— 从 R3〜R9 九轮对抗审查的真实 finding 归纳

同一张清单，两处用、两个视角：

- **修复方（Phase 2c，写代码之前）= 构造视角**：碰到左列的「代码种类」，**上来就套**右列的
  已知正确形状，一次写完；**禁止**先加一个 guard、被审出来再补第二个（R6→R9 四轮就是这么打转的：
  「删分支」这一个不可逆操作，被拆成 pre-check → TOCTOU → recheck-throw → delete-throw 四次补丁，
  而它本该在第一次就套「事务 reconciliation」形状一次写死）。
- **审查席（Phase 2 R1，穷举面）= 核对视角**：R1 必须逐条扫这九面，而不是「看到什么报什么」——
  A 类（既有代码的洞）要在一轮里挖净，不许分轮细水长流。

| # | 代码种类（修复方触发条件） | 已知正确形状（构造） | 审查核对点（这面漏了没） |
|---|---|---|---|
| 1 | **不可逆/破坏性操作**（删除、force-move、覆盖、rm、branch -D、update-ref -d） | **事务性 reconciliation 状态机**（见下方展开——**必须按状态机写，不是一串 guard**）：破坏性 step 无论**返回成功还是抛错**都进入同一个 reconcile；reconcile 内先分「**实际状态可观察 / 不可观察**」两支，不可观察时按最坏情况保守补偿 | 破坏性 step 之后每条 catch 是否都进了 reconcile？**观察器自身失败**这一支写了吗（这支最容易漏）？有没有 catch 直接 return 留下半损坏态？ |
| 2 | **共享可变资源 + 可能并发**（共享 ref/文件/worktree） | **CAS / 乐观**：check-then-act 之间必有窗口 → 用带 expected-old 的原子操作；破坏后复核发现竞态 → 补偿回滚 | 「检查」与「使用」之间是否有 TOCTOU 窗口？窗口内被抢占的后果是什么？ |
| 3 | **身份 / 归属判定** | **创建凭证**（创建时写 nonce/token，判定时比对）——内容相等（HEAD/hash/tip 撞值）**不等于**归属 | 判据是「内容相等」还是「创建时的凭证」？内容能不能被第三方撞值？ |
| 4 | **状态机 / 多阶段流程** | 不可逆状态一旦进入，**不许被重放/乱序调用清除**（如 replan 态不许被 allocate 重放抹掉） | 每个状态能否被重放、乱序、跳步清除？清除后能否绕回本该封死的分支？ |
| 5 | **同时有函数入口和 CLI 入口** | **两个入口同等 fail-closed**——不许 CLI 强制了、导出函数还 fail-open（in-process 调用方漏传即绕过） | 核心导出函数缺输入时是拒绝还是放行？CLI 的强制在函数层是否也在？ |
| 6 | **集合 / 覆盖判定** | 明确是 **exact 还是 subset** 并给理由——默认 exact（subset 能让漏项/幽灵项通过） | 是 exact 还是 subset？subset 的话漏项能不能过？ |
| 7 | **改文档 或 改契约** | 文档声称与实现要求**同步改**——按文档操作必须真能过守卫（否则第一次真用就死） | 按 SKILL/文档描述生成的输入，跑真守卫能过吗？还是只 grep 文档掩盖了断裂？ |
| 8 | **加/改门禁、守卫、测试** | 新测试必须**反证非空转**，且**红集恰好等于预测集**（见下方展开——先写下预测再跑，0 红或红集不等于预测都说明变异没构造对，不能当结论） | 反证做了吗？跑之前写下预测红集了吗？实际红集与预测**逐条**相符吗？该绿的确实绿着吗？ |
| 9 | **写保证等级 / 安全声称的文案** | 措辞不得夸大——T1（防疏忽/漂移）就说 T1，**不冒充** T2（防恶意伪造） | 文案读起来像在声称防恶意吗？实现实际只到防手滑吗？ |

## 第 1 类展开：事务性 reconciliation 状态机

R6→R9 四轮补丁螺旋的根因，是把这一个状态机拆成了四次「加 guard」。**一次写全下面五支**，
R7（检查-使用窗口）/ R8（观察器抛错）/ R9（破坏命令回执不确定）就都在初版里被覆盖：

```
① 前置：目标是否处于可安全破坏的状态？
   观察失败 → fail-closed 不动手（破坏前的异常也不许逃逸）
   不安全   → 拒绝
② 发起破坏性 step（带 expected-old 的原子操作，见第 2 类）
③ 无论成功/抛错，都进入 reconcile —— 不许任何 catch 直接 return
④ reconcile 先分两支（**这一分叉是关键，漏了就会长出 R8**）:
   ④a 实际状态**可观察** → 按实际态分支处置:
        · 仍在原位（破坏没发生）→ 安全记「拒绝」，不误报补偿
        · 已变更且属于我方预期后果 → 记成功
        · 已被第三方占据不同值 → **绝不覆盖**，记补偿失败交人工
   ④b 实际状态**不可观察**（观察器自身抛错/超时）→ **不可证明安全 = 按不安全处理**:
        直接尝试「不覆盖第三方」的保守补偿（如 old=全零的创建式 CAS），
        **不要**试图先读状态——失败的正是读状态本身
⑤ 补偿失败 → 显式记录（含完整 expected 值 + 各错误），交人工，绝不静默
```

反例记录（真实踩过）：R8 那轮就是把「观察器抛错」这支写成了 ④a 的形状（先读状态再补偿），
而失败的恰恰是读状态的命令 → 异常在补偿前逃逸，留下已损坏的对方 worktree。

## 第 8 类展开：反向变异的判据是「红集恰好等于预测集」

来源：另一会话在 mivo-canvas #419 的实测——同一个守卫文件上被连续找出三个绕过形态，
**三次都是构造变异发现的，没有一次是想出来的**。

**做法（顺序不能颠倒）**：① 只回退**一条规则**所依赖的**全部**代码，不多不少（隔离回退）；
② **跑之前先写下**「哪几条断言应该红、哪几条应该绿」；③ 跑，把实际红集与预测**逐条**对照。

| 变异结果 | 含义 | 危险度 |
|---|---|---|
| **红集 = 预测集** | 变异构造正确，这些断言确实在咬那条规则 | ✅ 唯一可用作结论的结果 |
| **0 红（假通过）** | 只还原了一半，其余半仍生效、违规照样被报出 | ⚠ **最危险**——看起来像「断言没在咬」，会诱使人去改**被测代码** |
| **红集 ⊋ 预测集** | 一次退了多条相互独立的规则 | 结论被污染，分不清哪条在咬 |
| **红集 ⊊ 预测集** | 预测里某条断言其实没在咬这条规则（空转，或被别处短路掩盖） | 有断言等于没断言，必须查出短路点 |
| **报错/编译失败** | 只换了判定条件、忘了同步还原配套代码（消息文本、变量引用） | 会误判成「修复无效」 |

**「恰好红 1 条」只是一条规则被一条断言守着时的特例，不是通用判据。**
一条规则被 N 条断言覆盖时，最小回退它必然红 N 条——这不是过宽对照，反而是**更强的鉴别**：
它同时给出正向（该红的全红了）与反向（不依赖该规则的全绿着）两侧证据。
关键区别在于「回退了几条规则」，不在于「红了几条断言」。

实证两则：
- 审查方验证一条 blanket claim 时连栽两次（先得 0 红、差点据此判声称不成立；再得 2 红——
  那次是真的一次退了两条独立规则），只有隔离回退才得到干净结论。
- hub 门 D1（可移除性判据）落地时，最小回退那一条判据 → 红 4 条（3 条场景 fixture + 1 条集成
  fixture），场景 1/5/6 保持绿。红集与预测逐条相符，结论成立；若当初硬套「必须恰好 1 红」，
  就会去拆本该一起红的断言，把鉴别力拆没了。

**完备性只能靠构造判定，不能靠推理**：「我目前再识别不到新形态了」这类声明在实际构造面前
反复被推翻。写「已覆盖 N 类」时，那个 N 只证明你构造了 N 个，**不证明只有 N 个**。

## 与第 5 类的一处张力：fail-closed 默认值会降低可观测性

给新参数配 fail-closed 默认值，方向是安全的，但它把「调用方漏传」从**报错**降级成**静默改变行为**。
在顶层 catch 且退出码恒 0 的脚本里，更优解是 **必填 + 入口校验 throw**——后果是「响亮但不致命」。
这与「退出码恒 0 让故障躲过绿灯」是同一个交换：**别用安全默认值换掉故障的可见性**。

## 用法边界

- 这九类不是穷尽，是**已被真实咬过**的九个。碰到不属于任何一类的新形状，仍按常识审/写；
  但**属于**某一类却没套对应形状 = 有效 finding（审查侧）/ 必须重写（修复侧）。
- 保证等级上限是 **T1**：这九条防的是疏忽与漂移，防不了同 UID 的故意伪造（脚本自身可被改，
  真 T2 需宿主级签名回执，本仓做不到）。任何一条读起来像在防恶意 → 见第 9 条。
