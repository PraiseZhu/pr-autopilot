## 第 1 类展开：事务性 reconciliation 状态机

R6→R9 四轮补丁螺旋的根因，是把这一个状态机拆成了四次「加 guard」。**一次写全下面五支**，
R7（检查-使用窗口）/ R8（观察器抛错）/ R9（破坏命令回执不确定）就都在初版里被覆盖：

```
① 前置：目标是否处于可安全破坏的状态？
   观察失败 → fail-closed 不动手（破坏前的异常也不许逃逸）
   不安全   → 拒绝
② 发起破坏性 step（带 expected-old 的原子操作，见第 2 类）
③ 无论成功/抛错，都进入 reconcile —— 不许任何 catch 直接 return
④ reconcile 先分两支（**这一分叉是关键，漏了就会长出 R8**）:
   ④a 实际状态**可观察** → 按实际态分支处置:
        · 仍在原位（破坏没发生）→ 安全记「拒绝」，不误报补偿
        · 已变更且属于我方预期后果 → 记成功
        · 已被第三方占据不同值 → **绝不覆盖**，记补偿失败交人工
   ④b 实际状态**不可观察**（观察器自身抛错/超时）→ **不可证明安全 = 按不安全处理**:
        直接尝试「不覆盖第三方」的保守补偿（如 old=全零的创建式 CAS），
        **不要**试图先读状态——失败的正是读状态本身
⑤ 补偿失败 → 显式记录（含完整 expected 值 + 各错误），交人工，绝不静默
```

反例记录（真实踩过）：R8 那轮就是把「观察器抛错」这支写成了 ④a 的形状（先读状态再补偿），
而失败的恰恰是读状态的命令 → 异常在补偿前逃逸，留下已损坏的对方 worktree。

> 命中检查点触发条件（见 `references/convergence-checkpoint.md`）→ 先做六件套，把破坏性
> step 涉及的全部事件/状态在事件×状态矩阵里过一遍，再回来套上面五支写；六件套不豁免这五支，
> 是这五支在触发条件命中时的前置动作。

## 第 4 类展开：显式状态机化（一般 async 生命周期形状）

**触发条件（D5，条件型）**：仅当改动命中**异步生命周期 + 重试/退避 + 取消 + 并发入口**这一
具体形状时套用本节（例如带重试的异步任务、可取消的长轮询、带心跳的连接管理）；对纯同步
代码、无重试无取消的简单状态切换**不强制**套用本节——第 4 类表格行里「不许被重放/乱序清除」
那条既有判据不受本节触发条件限制，始终适用。

命中该形状时的构造（来源：`review-convergence.md` §4）：

- 状态集中到一个 owner：例如 `Idle → Starting → Active → Backoff → Starting`，旁路
  `Cancelling` / `Settled`；
- 全部外部输入归一成事件：`startResolved / startRejected / timeout / turnStarted /
  outputProduced / overloaded / cancel / close / permissionChanged / turnCompleted /
  lateEvent`（按具体场景改名，形状不变——不许绕过 owner 直接改状态字段）；
- 用一个纯 transition 函数返回：下一状态、是否 interrupt、是否重试、是否落 tombstone、
  是否推送终态、是否释放派发锁；
- 用性质测试压组合爆炸，而不是逐条回归用例堆数量：同时最多一个有效 attempt；取消后的
  attempt 永不执行工具；每轮只产生一次终态；已产生输出的 attempt 不重放；外来/迟到事件
  不能结算当前请求；所有已受理 attempt 最终 settle 或进入有界重试。

> 命中检查点触发条件（见 `references/convergence-checkpoint.md`）→ 先做六件套，再决定是否
> 需要整块套用本节的状态机化——六件套的「事件×状态矩阵」正是本节 transition 函数的输入
> 来源：矩阵先枚举全貌，状态机把枚举结果实现成不可绕过的代码，两者是同一件事的前后两半。

## 第 8 类展开：反向变异的判据是「红集恰好等于预测集」

来源：另一会话在 mivo-canvas #419 的实测——同一个守卫文件上被连续找出三个绕过形态，
**三次都是构造变异发现的，没有一次是想出来的**。

**做法（顺序不能颠倒）**：① 只回退**一条规则**所依赖的**全部**代码，不多不少（隔离回退）；
② **跑之前先写下**「哪几条断言应该红、哪几条应该绿」；③ 跑，把实际红集与预测**逐条**对照。

| 变异结果 | 含义 | 危险度 |
|---|---|---|
| **红集 = 预测集** | 变异构造正确，这些断言确实在咬那条规则 | ✅ 唯一可用作结论的结果 |
| **0 红（假通过）** | 只还原了一半，其余半仍生效、违规照样被报出 | ⚠ **最危险**——看起来像「断言没在咬」，会诱使人去改**被测代码** |
| **红集 ⊋ 预测集** | 一次退了多条相互独立的规则 | 结论被污染，分不清哪条在咬 |
| **红集 ⊊ 预测集** | 预测里某条断言其实没在咬这条规则（空转，或被别处短路掩盖） | 有断言等于没断言，必须查出短路点 |
| **报错/编译失败** | 只换了判定条件、忘了同步还原配套代码（消息文本、变量引用） | 会误判成「修复无效」 |

**「恰好红 1 条」只是一条规则被一条断言守着时的特例，不是通用判据。**
一条规则被 N 条断言覆盖时，最小回退它必然红 N 条——这不是过宽对照，反而是**更强的鉴别**：
它同时给出正向（该红的全红了）与反向（不依赖该规则的全绿着）两侧证据。
关键区别在于「回退了几条规则」，不在于「红了几条断言」。

实证两则：
- 审查方验证一条 blanket claim 时连栽两次（先得 0 红、差点据此判声称不成立；再得 2 红——
  那次是真的一次退了两条独立规则），只有隔离回退才得到干净结论。
- hub 门 D1（可移除性判据）落地时，最小回退那一条判据 → 红 4 条（3 条场景 fixture + 1 条集成
  fixture），场景 1/5/6 保持绿。红集与预测逐条相符，结论成立；若当初硬套「必须恰好 1 红」，
  就会去拆本该一起红的断言，把鉴别力拆没了。

**完备性只能靠构造判定，不能靠推理**：「我目前再识别不到新形态了」这类声明在实际构造面前
反复被推翻。写「已覆盖 N 类」时，那个 N 只证明你构造了 N 个，**不证明只有 N 个**。

### 弱断言判据：`.length > 0` 只在输入只违反一条规则时安全

**判据**：形如 `ok(errs.length > 0)`（只判「有没有报错」，不点名具体错误）的断言，**仅在测试
输入只违反一条规则时安全**。一次摘掉/破坏多个字段，就必须逐字段 `.some((e) => /字段名/.test(e))`
各自点名——否则失败模式互相掩盖：A 检查被整段挖空后，B 的错误仍让 `.length > 0` 成立 → 测试
照绿，被挖空的那条规则没有任何测试钉住。

**实测案例（`fixtures/run-fixtures.mjs` 的 [R10-A3]⑤，2026-08-07）**：断言同时摘掉
`hardening_coverage` 与 `checklist_version` 两个字段，只判 `.length > 0`。把 hardening 全 round
强制整段挖空后，`checklist_version` 的错误仍让断言成立 → 测试照绿 → 那条 R3 改动此前没有任何
测试钉住。修法：拆成两条各自点名该字段的独立断言（`.some(/hardening_coverage/)` /
`.some(/checklist_version/)`）。对输入只违反一条规则的断言也统一升级为点名式——行为证据更强，
且防未来给同一输入加第二个违规字段时悄悄变弱（2026-08-07 对 [审②F1]/[e2e-consensus 缺口]/
[⑫] 三处实测：输入各只违反一条规则、挖空后断言均变红，断言有效，仍按此升级）。

**反向变异必须语义合法（三次失败换来的，别重犯）**——验证「某断言是否真绑定它声称验证的检查」
时，把该检查挖空做变异，下面两种变异**不算数**：

| 变异 | 为什么无效 |
|---|---|
| `need(false, …)` → `need(true, …)`（无条件不报错） | 若测试在**更早的失败断言**处中止，目标断言根本没执行到——红的是另一个失败模式，不是目标 |
| 改条件制造出真实代码不可能到达的状态（如 `if (!Array.isArray(items))` 改成 `… && v.round === 1`） | 崩溃 `Cannot read properties of undefined (reading 'length')`——items 是 undefined 却落进 else 分支。崩溃证明变异非法，不证明断言有效 |

**有效形态**（那次实测最终采用的）：把 `need(false, …)` 包进 `if (v.round === 1)`——对 round=2
输入不生效，等价于「该检查不存在」，且不改变任何可达状态。判据三条，缺一不可：

- 变异后必须**红在你想验的那条断言上**（看报错文案是不是它自己的）；
- 变异**不能造成崩溃**（崩溃证明变异非法，不证明断言有效）；
- 变异**不能让更早的断言先红**（否则目标断言没被执行）。

**「恰好红 1 条」不是目标，目标是失败模式互相隔离**：挖空 A 时红的那条，不能是挖空 B 时也会红
的同一条。与上方「红集恰好等于预测集」互补：那里管「一条规则」级别的回退对照，这里管「一条
断言」级别的变异定性。

### 检查点专项：可鉴别的半修法回归（SC-B5）

**触发条件**：命中 `references/convergence-checkpoint.md` 的检查点、或已知的半修法（如「只改了
resolve 分支没改 reject」）再次复发时追加这一项；首轮初次实现（没有「上一轮」可还原）不适用。

**做法**：① 精确还原上一轮那个有缺陷的补丁本身（或它的最小等价 mutation，确无法整份还原时用
等价 mutation 顶替）；② 跑前先写下预测：新测试对「上一轮补丁」应该红、对「本轮正确修法」应该
绿；③ 实跑，把实际红集与预测**逐条**对照。

**这是补充，不是替换**：上面「隔离回退一条规则的全部依赖代码」仍是主判据，证明的是规则本身
在咬；这一项额外证明的是**测试能分辨「正确修法」与「上一轮那种半修法」**。**整条规则回退变
红，不能证明测试能识别只修一半**——两者答的是不同问题，缺哪个都不完整：前者答「规则存在
效力」，后者答「规则细到能挡住这类更精细的缺陷」。
## 第 10 类展开：判据所有权与跨门兼容——两种形态不得互相顶替

「同一个东西被判了两次／判不过去」表面看都是「重复判断」，但根因是两种不同的形状，
**修法完全相反**——把①的药方（合并成一个 owner）用在②上会制造真实死锁（本节的 hub⊥coverage
实证）；把②的药方（放宽某个 gate）用在①上会重新长出「特例短路掩盖断言」（本清单第 8 类）。

### 形态①：同一语义在 ≥2 处独立判断（真重复，该合并）

同一件事被两段互不知情的代码各自判了一遍，判据可能还悄悄漂移（一处改了另一处没跟上）。

**正确形状**：找一个**单一 owner**（该语义的权威判定点），其余处改成**调用它**或**共享同一个
predicate 函数**——不是「删掉一处留另一处」（可能删错，留下判据更弱的那处），是让两处物理上
不可能出现两份定义。

**审查核对点**：这个语义是不是在两个文件/两个函数里各写了一份逻辑？改一处时另一处会不会忘了改？

### 形态②：不同 gate 各自合法地合取，组合出死锁（真死锁，不能合并，只能证明相容）

多个 gate 各自都是正确、独立成立的约束，但**同时**要求满足时，输入空间上不存在同时满足两者的
点——这不是「重复判断该合并」，恰恰是**只有一个判断点**（各 gate 各管一段，互不重叠）却仍然
死锁，合并两个 gate 只会把死锁焊进单一函数里，问题不会消失。

**正确形状**：
1. 列出**输入 × gate** 矩阵：每个 gate 对同一类输入各自允许哪些取值（allowed set）。
2. 证明各 gate 的 allowed set **交集非空**——不是「看起来应该没问题」，是针对边界输入
   （尤其是「最小规模」「单文件」这类退化情形）构造实例，跑真代码验证交集确实非空。
3. 交集为空 → 这不是 bug，是设计矛盾：出路可能是重设计其中一个 gate 的判据，也可能是
   **重审这个 gate 维护的属性配不配做阻断**（本节实证案例走的正是后者：「占比→可移除性」
   的判据重设计只解决了单文件退化例、次日就在单模块多文件上第二次死锁，最终 D2 把并行度
   从 correctness gate 降为人工确认记录——见下方实证案例的时序）。不是删掉某个 gate、
   也不是加特例豁免。
4. 相容性证明落成**回归测试锁住**——防止未来任何一次「看起来合理」的局部修改（哪怕两个 gate
   各自的单元测试都仍然绿）悄悄破坏这个交集。

**审查核对点**：这几个 gate 是不是各自独立成立、却可能同时对同一输入生效？有没有针对边界/退化
输入构造实例验证过它们的 allowed set 交集非空？如果只改了其中一个 gate，会不会需要重新验证？

**实证案例（真实死锁，非理论风险，2026-08-02 实测）**：hub 门（fix-plan.mjs 的广域锚点识别）
与 coverage 门（sc-coverage-gate.mjs 的 SC-4 一对一双射）各自独立、各自都是正确的约束。但在
**单文件 PR**（3 条 blocker/major finding 全部只能锚在同一个文件）场景下：coverage 门要求这
3 条 finding 各自被**恰好 1 条** SC 覆盖、且这 3 条 SC 不能合并成一条（SC-4 禁 mega-SC）；hub
门（旧判据：单一路径占比 > 50% 且 ≥3 条 SC 共享 → degraded）看到这 3 条 SC 全部共享同一个文件
路径，会判定为「广域锚点污染」而 degraded——但 origin 席根本没有第二个文件可拆锚点（这 3 条
finding 客观上就是同一份代码的三处独立问题），此时 hub 门的 allowed set（要求锚点分散）与
coverage 门的 allowed set（要求每条 SC 独立引用且不可合并）**交集为空**，push 永远过不去。
当时的缓解（D1，2026-08-02）：把 hub 门的判据从「占比」换成「可移除性」——单文件场景死锁消除。
**但 D1 是历史缓解，不是终解**：第二天（2026-08-03）mivo-canvas 又在「单模块多文件」形状上
死锁（10 条缺陷真在 gate.mjs、每条也真碰 gate.test.mjs，allRemovable 为真照样 degraded）。
现行方案（D2，fable 裁决 2026-08-03）：**保留检测、取消阻断**——hub 命中落
`plan.parallelism_notes`（联合度量的真实并行度损失），进 `fix_plan_hash`，由 lead 读后确认
（消费动作见 SKILL Phase 2c）。所以现在谈不上「hub 门的拦截力」——它不再拦截任何东西，
这是有意为之：并行度不是正确性属性，机器也分辨不出合法同模块耦合与锚点污染，分辨不出
就不该下阻断判决。它的价值改为「损失被如实记录、被人读到」。**不得**把这个案例误读成「hub
门和 coverage 门重复判断了同一件事，合并掉一个就好」——合并会让 hub 门失去独立存在的意义
（它本来就该管「文件域是不是被广列」，coverage 门管「finding 有没有被覆盖」，两者管的不是同一
语义，只是恰好在退化输入上合取出了空集，属于形态②不是形态①）。

## 与第 5 类的一处张力：fail-closed 默认值会降低可观测性

给新参数配 fail-closed 默认值，方向是安全的，但它把「调用方漏传」从**报错**降级成**静默改变行为**。
在顶层 catch 且退出码恒 0 的脚本里，更优解是 **必填 + 入口校验 throw**——后果是「响亮但不致命」。
这与「退出码恒 0 让故障躲过绿灯」是同一个交换：**别用安全默认值换掉故障的可见性**。

## 新增机制确认门（净新增基础设施前必答，不是十类之一）

净新增并发/锁/缓存/持久化/重试类基础设施前必须先答一句：**删掉这个机制，PR 原始目标还
成立吗？**

- 成立 → 默认删（把删除当默认动作，不是「可以考虑删」）。
- 不成立 → worker 提交最小替代方案 + 成本 + 失败面，**暂停该 SC**、等 owner 决策，**不
  阻塞**同一 fix-plan 里其他无关的 SC。

**这是「修复方按 SC 自主执行」的窄例外**：普通的局部实现选择（用哪个数据结构、拆不拆函数）
不触发本门，只有「净新增」一整类机制才触发。owner 决策范围按 `convergence-checkpoint.md`
D3——拆 PR、净新增基础设施、用户可见行为/功能范围/发布策略变更需要 owner；纯技术升级路径
（状态机化/职责上移/降级）lead 自主选。

实证：`review-convergence.md` §3 记录的 `#1211`——一个 UI 兜底问题的修复过程中长出了一整套
锁子系统，25 轮后被整体扔掉才合并；若在写锁子系统**之前**先问一句「删掉它 PR 目标还成立
吗」，答案本该是「成立」（UI 兜底不需要锁），25 轮可以省下。

## 用法边界

- 这十类不是穷尽，是**已被真实咬过**的十个。碰到不属于任何一类的新形状，仍按常识审/写；
  但**属于**某一类却没套对应形状 = 有效 finding（审查侧）/ 必须重写（修复侧）。
- 保证等级上限是 **T1**：这十条防的是疏忽与漂移，防不了同 UID 的故意伪造（脚本自身可被改，
  真 T2 需宿主级签名回执，本仓做不到）。任何一条读起来像在防恶意 → 见第 9 条。
