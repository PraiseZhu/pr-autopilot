# 加固清单（九类）— 从 R3〜R9 九轮对抗审查的真实 finding 归纳

同一张清单，两处用、两个视角：

- **修复方（Phase 2c，写代码之前）= 构造视角**：碰到左列的「代码种类」，**上来就套**右列的
  已知正确形状，一次写完；**禁止**先加一个 guard、被审出来再补第二个（R6→R9 四轮就是这么打转的：
  「删分支」这一个不可逆操作，被拆成 pre-check → TOCTOU → recheck-throw → delete-throw 四次补丁，
  而它本该在第一次就套「事务 reconciliation」形状一次写死）。
- **审查席（Phase 2 R1，穷举面）= 核对视角**：R1 必须逐条扫这九面，而不是「看到什么报什么」——
  A 类（既有代码的洞）要在一轮里挖净，不许分轮细水长流。

| # | 代码种类（修复方触发条件） | 已知正确形状（构造） | 审查核对点（这面漏了没） |
|---|---|---|---|
| 1 | **不可逆/破坏性操作**（删除、force-move、覆盖、rm、branch -D、update-ref -d） | **事务性 reconciliation**：发起破坏性 step 后，其后**每一个**异常出口（包括复核命令自身抛错、删除命令抛错）都必须先读实际状态再补偿，绝不「当作没发生」直接返回。不是一串 guard | 破坏性 step 之后的每条 catch 是否都走了补偿？有没有 catch 直接 return 留下半损坏态？ |
| 2 | **共享可变资源 + 可能并发**（共享 ref/文件/worktree） | **CAS / 乐观**：check-then-act 之间必有窗口 → 用带 expected-old 的原子操作；破坏后复核发现竞态 → 补偿回滚 | 「检查」与「使用」之间是否有 TOCTOU 窗口？窗口内被抢占的后果是什么？ |
| 3 | **身份 / 归属判定** | **创建凭证**（创建时写 nonce/token，判定时比对）——内容相等（HEAD/hash/tip 撞值）**不等于**归属 | 判据是「内容相等」还是「创建时的凭证」？内容能不能被第三方撞值？ |
| 4 | **状态机 / 多阶段流程** | 不可逆状态一旦进入，**不许被重放/乱序调用清除**（如 replan 态不许被 allocate 重放抹掉） | 每个状态能否被重放、乱序、跳步清除？清除后能否绕回本该封死的分支？ |
| 5 | **同时有函数入口和 CLI 入口** | **两个入口同等 fail-closed**——不许 CLI 强制了、导出函数还 fail-open（in-process 调用方漏传即绕过） | 核心导出函数缺输入时是拒绝还是放行？CLI 的强制在函数层是否也在？ |
| 6 | **集合 / 覆盖判定** | 明确是 **exact 还是 subset** 并给理由——默认 exact（subset 能让漏项/幽灵项通过） | 是 exact 还是 subset？subset 的话漏项能不能过？ |
| 7 | **改文档 或 改契约** | 文档声称与实现要求**同步改**——按文档操作必须真能过守卫（否则第一次真用就死） | 按 SKILL/文档描述生成的输入，跑真守卫能过吗？还是只 grep 文档掩盖了断裂？ |
| 8 | **加/改门禁、守卫、测试** | 新测试必须**反证非空转**：撤掉修复 → 对应 fixture 必须变红 → 恢复 | 撤掉这条修复，有没有对应 fixture 变红？还是测试恒绿？ |
| 9 | **写保证等级 / 安全声称的文案** | 措辞不得夸大——T1（防疏忽/漂移）就说 T1，**不冒充** T2（防恶意伪造） | 文案读起来像在声称防恶意吗？实现实际只到防手滑吗？ |

## 用法边界

- 这九类不是穷尽，是**已被真实咬过**的九个。碰到不属于任何一类的新形状，仍按常识审/写；
  但**属于**某一类却没套对应形状 = 有效 finding（审查侧）/ 必须重写（修复侧）。
- 保证等级上限是 **T1**：这九条防的是疏忽与漂移，防不了同 UID 的故意伪造（脚本自身可被改，
  真 T2 需宿主级签名回执，本仓做不到）。任何一条读起来像在防恶意 → 见第 9 条。
